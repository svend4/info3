Временная сложность (Time Complexity):
T(n) = O(f(n))

где:
n — размер входных данных
f(n) — функция роста времени выполнения

Иерархия сложности (от быстрой к медленной):
O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ) < O(n!)

Примеры:
• O(1) — константное время: доступ к элементу массива по индексу
• O(log n) — логарифмическое: бинарный поиск
• O(n) — линейное: проход по массиву
• O(n log n) — линейно-логарифмическое: эффективная сортировка (merge sort)
• O(n²) — квадратичное: пузырьковая сортировка, вложенные циклы
• O(2ⁿ) — экспоненциальное: перебор всех подмножеств
• O(n!) — факториальное: перебор всех перестановок

Пространственная сложность (Space Complexity):
S(n) = O(g(n))

Trade-off между временем и памятью:
Time ↔ Space

→ Быстрые алгоритмы часто требуют больше памяти
→ Экономия памяти часто замедляет выполнение

┌────────────────────────────────────────────────────────────────────────────┐
│ [2] АРХЕТИП — Развёрнутая формула с компонентами                           │
└────────────────────────────────────────────────────────────────────────────┘

Algorithm = (Problem × Strategy) × (Complexity × Correctness) × (Implementation)

Компоненты:

Problem (Проблема):
├─ Input: входные данные
├─ Output: желаемый результат
├─ Constraints: ограничения (время, память)
└─ Edge cases: граничные случаи

Strategy (Стратегия):
├─ Brute Force: полный перебор (простой, но медленный)
├─ Divide and Conquer: разделяй и властвуй (merge sort, quick sort)
├─ Dynamic Programming: запоминание решений подзадач
├─ Greedy: жадные алгоритмы (локально оптимальный выбор)
├─ Backtracking: возврат при неудаче (судоку, N-ферзей)
├─ Branch and Bound: отсечение неперспективных вариантов
└─ Heuristics: эвристики для приближённого решения

Complexity (Сложность):
├─ Best case: лучший сценарий
├─ Average case: средний случай
├─ Worst case: худший случай (обычно важнейший)
└─ Amortized: амортизированная (среднее по последовательности операций)

Correctness (Корректность):
├─ Proof: математическое доказательство
├─ Loop invariant: инвариант цикла
├─ Testing: тестирование на примерах
└─ Edge cases: проверка граничных случаев

Фундаментальные алгоритмы:

1. СОРТИРОВКА:
   
   Сравнением:
   ├─ Bubble Sort: O(n²) — простой, но медленный
   ├─ Selection Sort: O(n²) — минимум/максимум на каждом шаге
   ├─ Insertion Sort: O(n²) — хорош для почти отсортированных
   ├─ Merge Sort: O(n log n) — стабильный, предсказуемый
   ├─ Quick Sort: O(n log n) average, O(n²) worst — быстрый на практике
   ├─ Heap Sort: O(n log n) — in-place, без дополнительной памяти
   └─ Tim Sort: O(n log n) — Python/Java стандарт (hybrid merge+insertion)
   
   Без сравнений:
   ├─ Counting Sort: O(n+k) — для ограниченного диапазона
   ├─ Radix Sort: O(d×n) — сортировка по разрядам
   └─ Bucket Sort: O(n+k) — распределение по корзинам

2. ПОИСК:
   
   ├─ Linear Search: O(n) — проход по массиву
   ├─ Binary Search: O(log n) — в отсортированном массиве
   ├─ Hash Table: O(1) average — поиск по ключу
   ├─ Binary Search Tree: O(log n) average, O(n) worst
   ├─ Balanced BST (AVL, Red-Black): O(log n) гарантированно
   └─ Trie: O(m) где m — длина ключа (для строк)

3. ГРАФЫ:
   
   Обход:
   ├─ DFS (Depth-First Search): O(V+E) — в глубину, stack/recursion
   └─ BFS (Breadth-First Search): O(V+E) — в ширину, queue
   
   Кратчайший путь:
   ├─ Dijkstra: O((V+E) log V) — неотрицательные веса
   ├─ Bellman-Ford: O(V×E) — работает с отрицательными весами
   ├─ Floyd-Warshall: O(V³) — все пары вершин
   └─ A*: эвристический поиск (например, для карт)
   
   Минимальное остовное дерево:
   ├─ Kruskal: O(E log E) — сортировка рёбер
   └─ Prim: O((V+E) log V) — жадное построение
   
   Топологическая сортировка: O(V+E) — для DAG

4. ДИНАМИЧЕСКОЕ ПРОГРАММИРОВАНИЕ:
   
   Классические задачи:
   ├─ Fibonacci: O(n) вместо O(2ⁿ)
   ├─ Knapsack (Рюкзак): O(n×W)
   ├─ Longest Common Subsequence: O(m×n)
   ├─ Edit Distance (Левенштейн): O(m×n)
   ├─ Matrix Chain Multiplication: O(n³)
   └─ Coin Change: O(n×amount)
   
   Подходы:
   ├─ Top-down (Memoization): рекурсия + кеш
   └─ Bottom-up (Tabulation): заполнение таблицы

5. СТРОКИ:
   
   ├─ Pattern Matching: O(n×m) naive, O(n+m) KMP/Boyer-Moore
   ├─ Rabin-Karp: O(n+m) average — хеширование
   ├─ Aho-Corasick: O(n+m+z) — множественный поиск
   ├─ Suffix Array: O(n log n) — все суффиксы
   └─ Z-algorithm: O(n) — pattern matching

6. ЧИСЛОВЫЕ:
   
   ├─ Euclidean GCD: O(log min(a,b)) — НОД
   ├─ Fast Exponentiation: O(log n) — быстрое возведение в степень
   ├─ Sieve of Eratosthenes: O(n log log n) — простые числа
   ├─ Fast Fourier Transform: O(n log n) — обработка сигналов
   └─ Karatsuba: O(n^1.585) — быстрое умножение больших чисел

Структуры данных (важны для алгоритмов):

├─ Array: O(1) access, O(n) insert/delete
├─ Linked List: O(n) access, O(1) insert/delete at known position
├─ Stack: O(1) push/pop — LIFO
├─ Queue: O(1) enqueue/dequeue — FIFO
├─ Hash Table: O(1) average для всех операций
├─ Binary Search Tree: O(log n) average
├─ Heap: O(log n) insert/delete, O(1) find-min/max
├─ Trie: O(m) для строк длины m
└─ Union-Find (Disjoint Set): O(α(n)) ≈ O(1) — почти константа

ПРИМЕР: Задача "Two Sum"

Задача: Найти два числа в массиве, сумма которых равна target.

ШАГ 1: ПОНИМАНИЕ
• Вход: массив чисел + target
• Выход: индексы двух чисел
• Ограничения: каждый элемент использовать один раз
• Edge cases: нет решения, несколько решений, дубликаты

ШАГ 2: ПРИМЕРЫ
```
Input: [2, 7, 11, 15], target = 9
Output: [0, 1]  (2 + 7 = 9)

Input: [3, 2, 4], target = 6
Output: [1, 2]  (2 + 4 = 6)
```

ШАГ 3: СТРАТЕГИИ

Подход 1: Brute Force
```
for i in range(len(nums)):
    for j in range(i+1, len(nums)):
        if nums[i] + nums[j] == target:
            return [i, j]
```
Time: O(n²), Space: O(1)
→ Медленно для больших массивов

Подход 2: Hash Table
```
seen = {}
for i, num in enumerate(nums):
    complement = target - num
    if complement in seen:
        return [seen[complement], i]
    seen[num] = i
```
Time: O(n), Space: O(n)
→ Быстро! Trade-off: используем память

ШАГ 4: АНАЛИЗ
Hash Table подход оптимален: O(n) время, O(n) память
Лучше чем O(n²) brute force

ШАГ 5: РЕАЛИЗАЦИЯ
(см. код выше)

ШАГ 6: ТЕСТИРОВАНИЕ
• [2,7,11,15], target=9 → [0,1] ✓
• [3,2,4], target=6 → [1,2] ✓
• [3,3], target=6 → [0,1] ✓
• [], target=0 → None или exception

ШАГ 7: ОПТИМИЗАЦИЯ
Для данной задачи O(n) — оптимум (нужно хотя бы просмотреть массив).
Дальнейшая оптимизация: константы, читаемость кода.

ОБЪЯСНЕНИЕ:

Два противоречащих принципа, которые нужно балансировать:

1. "Преждевременная оптимизация — корень всех зол" (Дональд Кнут):
   • Не оптимизируйте код до того, как узнаете, что он медленный
   • Сначала работающий код, потом быстрый
   • 90% времени программа тратит в 10% кода — оптимизируйте эти 10%
   • Readable code > Clever code

2. НО: Алгоритмическая сложность имеет значение:
   • O(n²) vs O(n) — это не микрооптимизация, это архитектурное решение
   • Выбор структуры данных критичен
   • O(2ⁿ) не спасёт никакое железо при n > 30

БАЛАНС:
• Не пишите O(n³) алгоритм, когда есть O(n log n)
• НО не оптимизируйте константы до измерения
• Профилируй, не гадай: measure, don't guess

ПРАВИЛО БОЛЬШОГО ПАЛЬЦА:
1. Сначала правильный алгоритм (правильная сложность)
2. Потом работающий код (проходит тесты)
3. Потом читаемый код (легко поддерживать)
4. Потом быстрый код (только если нужно)

ПРОБЛЕМА (1998):
Как ранжировать веб-страницы в поисковой выдаче?

СТАРЫЕ ПОДХОДЫ:
• Подсчёт ключевых слов → спам
• Мета-теги → веб-мастера обманывали
• Yahoo: ручная категоризация → не масштабируется

ИНСАЙТ ЛАРРИ ПЕЙДЖА:
"Ссылка — это голос. Но не все голоса равны."

АЛГОРИТМ PAGERANK:

Идея: Рекурсивное определение важности страницы
```
PR(A) = (1-d) + d × Σ(PR(Tᵢ) / C(Tᵢ))

где:
PR(A) — PageRank страницы A
d — damping factor (обычно 0.85)
Tᵢ — страницы, ссылающиеся на A
C(Tᵢ) — количество исходящих ссылок с Tᵢ
```

ИНТЕРПРЕТАЦИЯ:
"Random surfer" модель:
• Пользователь с вероятностью 85% переходит по ссылке
• С вероятностью 15% переходит на случайную страницу
• PageRank = вероятность оказаться на странице

РЕАЛИЗАЦИЯ:
• Граф из миллиардов страниц (вершин) и ссылок (рёбер)
• Итеративное вычисление: повторять пока не сходится
• Матричное умножение: оптимизация через sparse matrices
• MapReduce: распределённое вычисление

СЛОЖНОСТЬ:
• Time: O(iterations × edges) — линейная от размера графа
• Space: O(pages) — нужно хранить PR всех страниц
• Проблема: миллиарды страниц, но алгоритм линейный → масштабируется

РЕЗУЛЬТАТ:
• Google победил AltaVista, Yahoo, и других
• Качество поиска на порядок выше
• Основа для $2 trillion компании

ЭВОЛЮЦИЯ:
• 2000-е: PageRank + сотни других факторов
• 2010-е: Machine Learning начинает доминировать
• 2020-е: RankBrain (нейросети), BERT
• НО: PageRank остаётся базовым компонентом

УРОК:
Умный алгоритм может победить грубую силу.
PageRank использовал структуру веба (граф ссылок), которую игнорировали другие.

┌────────────────────────────────────────────────────────────────────────────┐
│ ПРИМЕР 2: Quick Sort — элегантность divide and conquer                    │
└────────────────────────────────────────────────────────────────────────────┘

ЗАДАЧА:
Отсортировать массив чисел.

НАИВНЫЙ ПОДХОД:
Bubble Sort: O(n²)
```python
for i in range(n):
    for j in range(n-1):
        if arr[j] > arr[j+1]:
            swap(arr[j], arr[j+1])
```
→ Медленно для больших массивов

QUICK SORT ПОДХОД (Tony Hoare, 1959):

Идея: Divide and Conquer
1. Выбрать pivot (опорный элемент)
2. Разделить массив: меньше pivot | pivot | больше pivot
3. Рекурсивно отсортировать обе части

```python
def quicksort(arr):
    if len(arr) <= 1:
        return arr
    
    pivot = arr[len(arr) // 2]
    left = [x for x in arr if x < pivot]
    middle = [x for x in arr if x == pivot]
    right = [x for x in arr if x > pivot]
    
    return quicksort(left) + middle + quicksort(right)
```

СЛОЖНОСТЬ:
• Best/Average case: O(n log n)
  - Каждый уровень рекурсии: O(n) работы
  - Глубина рекурсии: O(log n) при хорошем разбиении
  
• Worst case: O(n²)
  - Когда pivot всегда минимум/максимум
  - Пример: уже отсортированный массив с плохим выбором pivot
  - Решение: random pivot или median-of-three

• Space: O(log n) для рекурсии

ПОЧЕМУ QUICK SORT ПОПУЛЯРЕН?

1. На практике БЫСТРЕЕ merge sort:
   • Лучшая cache locality
   • Меньше операций перемещения данных
   • In-place версия (без доп. памяти)

2. Average case O(n log n):
   • Worst case O(n²) редок при random pivot
   • Практически всегда быстрый

3. Простота реализации:
   • Понятная идея
   • Короткий код

СТАНДАРТ:
• C qsort(): Quick Sort (с оптимизациями)
• Python: Timsort (hybrid), но QuickSort для примитивов в некоторых реализациях
• Java: Dual-Pivot QuickSort для примитивов

ОПТИМИЗАЦИИ:
• Random pivot: избежать worst case
• Median-of-three: pivot = median(first, middle, last)
• Insertion sort для малых подмассивов (< 10 элементов)
• Tail recursion optimization: избежать stack overflow

УРОК:
Простая идея (divide and conquer) + хорошая реализация = эффективный алгоритм.
Quick Sort — пример элегантного решения с практической пользой.

КОНКУРС (2006-2009):
Netflix объявила: $1 млн за алгоритм рекомендаций, который улучшит их систему 
на 10% (по метрике RMSE).

ЗАДАЧА:
Collaborative Filtering — предсказать рейтинг пользователя для фильма.

ДАННЫЕ:
• 100 млн рейтингов
• 480,000 пользователей
• 17,000 фильмов
• Матрица: users × movies (очень sparse, 99% пусто)

BASELINE (Netflix Cinematch):
RMSE = 0.9514
Цель: RMSE < 0.8563 (10% улучшение)

ПОДХОДЫ УЧАСТНИКОВ:

1. MATRIX FACTORIZATION:
   Идея: разложить матрицу рейтингов на user factors × movie factors
   ```
   Rating(u, m) ≈ Σ(user_factor[u][k] × movie_factor[k][m])
   ```
   • Размерность k = 50-100 (latent factors)
   • Обучение: SGD (Stochastic Gradient Descent)
   • Регуляризация: предотвращение overfitting

2. ENSEMBLE METHODS:
   • Комбинация сотен моделей
   • Blending: взвешенное среднее предсказаний
   • Stacking: meta-model на выходах других моделей

3. TEMPORAL DYNAMICS:
   • Учёт изменения вкусов со временем
   • Seasonal effects: рождественские фильмы в декабре
   • Movie aging: старые фильмы оцениваются по-другому

ПОБЕДИТЕЛИ (2009):
BellKor's Pragmatic Chaos:
• RMSE = 0.8558 (10.06% улучшение)
• 107 разных алгоритмов в ансамбле
• Gradient Boosted Decision Trees + SVD + RBM + ...

ИРОНИЯ:
Netflix НЕ ВНЕДРИЛА победившее решение!

ПРИЧИНЫ:
1. Сложность:
   • 107 моделей — кошмар поддержки
   • Обучение занимает недели
   • Требует огромные вычислительные ресурсы

2. Инженерные затраты:
   • Стоимость внедрения > выгода от 10% улучшения
   • Простота системы важнее точности

3. Изменение бизнеса:
   • 2009-2012: переход от DVD к стриминг
   • Implicit feedback (просмотры) важнее explicit (рейтингов)
   • Realtime рекомендации важнее офлайн точности

• Deep Learning модели
• Reinforcement Learning
• Context-aware: время суток, устройство, история
• A/B тестирование: измеряем engagement, не RMSE

УРОК:
"Лучший алгоритм" на бумаге ≠ лучшее решение в продакшене.

Trade-offs:
• Accuracy vs Complexity
• Offline metrics vs Online business metrics
• Engineering cost vs Model improvement

"В продакшене простой алгоритм, который работает, лучше сложного,
который работает на 10% лучше, но требует 10x ресурсов"

┌────────────────────────────────────────────────────────────────────────────┐
│ ПРИМЕР 4: Алгоритмическая катастрофа — Stack Overflow outage (2016)       │
└────────────────────────────────────────────────────────────────────────────┘

ИНЦИДЕНТ (20 июля 2016):
Stack Overflow недоступен 34 минуты. Причина: REGEX.

ЧТО ПРОИЗОШЛО:

Пользователь опубликовал пост с текстом, содержащим:
```
"title": "Помогите с regex для парсинга xxx"
```

Текст содержал строку, которая вызвала КАТАСТРОФИЧЕСКУЮ ОБРАТНУЮ 
ПРОКРУТКУ (catastrophic backtracking) в регулярном выражении.

REGEX ПРОБЛЕМА:

Плохой regex (упрощённо):
```
(a+)+b
```

Попытка сопоставить со строкой без 'b' в конце:
```
"aaaaaaaaaaaaaaaaaaaaaaaaa"
```

ЧТО ПРОИСХОДИТ:
• Regex engine пытается все возможные группировки 'a'
• (a)(a)(a)(a)...(a)
• (aa)(a)(a)...(a)
• (a)(aa)(a)...(a)
• ... экспоненциальное количество вариантов

СЛОЖНОСТЬ:
O(2ⁿ) где n — количество символов!

Для 25 символов: 2²⁵ = 33 миллиона попыток

РЕЗУЛЬТАТ:
• CPU загрузка 100%
• Сервер перестал отвечать
• Cascading failure: другие серверы тоже упали
• 34 минуты downtime

ИСПРАВЛЕНИЕ:
1. Немедленное:
   • Удалили проблемный пост
   • Перезапустили серверы

2. Долгосрочное:
   • Timeout для regex matching
   • Валидация regex перед применением
   • Мониторинг CPU usage для regex

ТЕХНИЧЕСКАЯ ДЕТАЛЬ:

Хороший regex:
```
a+b
```
→ O(n) сложность, линейная

Плохой regex:
```
(a+)+b
```
→ O(2ⁿ) сложность, экспоненциальная

Разница: вложенные квантификаторы создают backtracking.

УРОК:
Алгоритмическая сложность — это не абстракция.

• O(2ⁿ) означает: 10 символов = 1024 операции
                   20 символов = 1 млн операций
                   30 символов = 1 млрд операций → минуты работы

• Даже "простые" операции (regex) могут иметь ужасную сложность

• Input validation критична:
  - Не доверяйте пользовательскому вводу
  - Ограничивайте размер входных данных
  - Timeout для потенциально опасных операций

"Один плохой regex может положить весь сайт"

ПРАКТИЧЕСКИЕ РЕКОМЕНДАЦИИ:

1. ДЛЯ РАЗРАБОТЧИКОВ:

   Изучайте фундаментальные алгоритмы:
   • Sorting: Quick Sort, Merge Sort
   • Search: Binary Search, Hash Tables
   • Graphs: DFS, BFS, Dijkstra
   • Dynamic Programming: основные паттерны
   
   Анализируйте сложность:
   • Всегда думайте: "Какая сложность у этого кода?"
   • Вложенные циклы = минимум O(n²)
   • Избегайте O(2ⁿ) и O(n!) если n > 20
   
   Используйте правильные структуры данных:
   • Нужен быстрый поиск? → Hash Table / Set
   • Нужен порядок? → Sorted Array / BST
   • Нужны приоритеты? → Heap / Priority Queue
   • Нужна история операций? → Stack / Queue

2. ДЛЯ ИНТЕРВЬЮ:

   Подготовка:
   • LeetCode, HackerRank, CodeForces
   • Практикуйте объяснение решений
   • Учитесь думать вслух
   
   На интервью:
   • Сначала brute force, потом оптимизация
   • Обсудите trade-offs
   • Тестируйте edge cases
   • Анализируйте сложность
   
   Паттерны:
   • Two Pointers: для массивов
   • Sliding Window: для подмассивов
   • Fast & Slow pointers: для linked lists
   • Merge Intervals: для интервалов
   • Top K elements: heap
   • Tree DFS/BFS: рекурсия/queue

3. ДЛЯ ПРОДАКШЕНА:

   Выбор алгоритма:
   • Simple > Clever
   • Maintainable > Slightly faster
   • Measure before optimizing
   
   Профилирование:
   • Python: cProfile, line_profiler
   • Java: JProfiler, YourKit
   • Identify bottlenecks: 90/10 правило
   
   Оптимизация:
   1. Правильный алгоритм (O(n) vs O(n²))
   2. Правильная структура данных
   3. Кеширование результатов
   4. Распараллеливание
   5. Hardware (последний resort)

4. ОБЩИЕ ПРИНЦИПЫ:

   Закон Амдала:
   • Ускорение ограничено последовательными частями
   • Оптимизировать нужно bottlenecks, не всё подряд
   
   Принцип Парето (80/20):
   • 80% времени в 20% кода
   • Найдите эти 20% и оптимизируйте их
   
   YAGNI (You Aren't Gonna Need It):
   • Не пишите O(n log n) если у вас n < 100
   • Простота часто важнее теоретической оптимальности

ЗАКЛЮЧЕНИЕ:

Алгоритмы — это фундамент computer science. Понимание алгоритмической 
сложности отличает хорошего программиста от великого.

КЛЮЧЕВЫЕ ИНСАЙТЫ:

1. Сложность имеет значение:
   → O(n) vs O(n²) — это не детали, это архитектура
   → Правильный алгоритм важнее быстрого кода

2. Trade-offs повсюду:
   → Time vs Space
   → Simplicity vs Performance
   → Theoretical optimal vs Practical best

3. Контекст критичен:
   → n = 10? Любой алгоритм подойдёт
   → n = 10⁶? Нужен O(n log n)
   → n = 10⁹? Только O(n) или O(log n)

4. Реальный мир сложен:
   → Cache effects, branch prediction, memory latency
   → Offline metrics ≠ Online business value
   → Simple working > Complex theoretical optimal

Алгоритмы — это инструменты. Мастерство — в выборе правильного 
инструмента для конкретной задачи.

"Algorithm is the soul of computation" — Niklaus Wirth
