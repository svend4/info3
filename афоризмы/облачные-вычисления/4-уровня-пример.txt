Cloud Value = (Scalability + Availability + Flexibility) / (CapEx + OpEx)

где:
Scalability — возможность масштабирования по требованию
Availability — доступность сервисов (% uptime)
Flexibility — гибкость (быстрое изменение ресурсов)
CapEx (Capital Expenditure) — капитальные затраты (hardware, дата-центры)
OpEx (Operational Expenditure) — операционные затраты (аренда, обслуживание)

Ценностное предложение облака:
- CapEx → OpEx: из "владения" в "аренду"
- Pay-as-you-go: платишь только за используемое
- Elastic: ресурсы растут/уменьшаются автоматически

Модели обслуживания:

Infrastructure = IaaS (Infrastructure as a Service)
Platform = PaaS (Platform as a Service)
Software = SaaS (Software as a Service)

Ответственность:
IaaS: пользователь управляет OS, приложениями
PaaS: пользователь управляет только приложениями
SaaS: провайдер управляет всем

Модели развёртывания:

Public Cloud: общие ресурсы, многопользовательские (AWS, Azure, GCP)
Private Cloud: выделенные ресурсы, одна организация
Hybrid Cloud: комбинация Public + Private
Multi-Cloud: использование нескольких провайдеров

АРХЕТИП ОБЛАЧНОЙ ИНФРАСТРУКТУРЫ

Облачное решение = (Виртуализация × Оркестрация × API) ×
                   (Глобальная инфраструктура + Managed Services) ÷
                   (Vendor Lock-in + Сложность + Security Concerns) ×
                   Автоматизация

где компоненты детализированы:

• ВИРТУАЛИЗАЦИЯ — фундамент облака:

  COMPUTE VIRTUALIZATION:
  ├─ Гипервизоры: VMware ESXi, KVM, Xen, Hyper-V
  ├─ Виртуальные машины (VM): изолированные OS на одном физическом сервере
  ├─ Контейнеры: Docker, Kubernetes — легковесная альтернатива VM
  │  └─ Контейнер != VM: делят kernel, но изолированы process-level
  └─ Serverless: FaaS (Function as a Service) — код без управления серверами

  Преимущества виртуализации:
  - Efficiency: один сервер → множество VM (утилизация 70-90% vs 10-20%)
  - Isolation: сбой одной VM не влияет на другие
  - Flexibility: создание/удаление VM за минуты vs недели для физических

  NETWORK VIRTUALIZATION:
  ├─ VPC (Virtual Private Cloud): изолированная сетевая зона в облаке
  ├─ Subnets: разделение сети (public, private)
  ├─ Security Groups: firewall rules для ресурсов
  ├─ Load Balancers: распределение трафика между инстансами
  └─ VPN/Direct Connect: защищённое подключение on-premise ↔ cloud

  STORAGE VIRTUALIZATION:
  ├─ Block Storage: EBS (AWS), Managed Disks (Azure) — виртуальные диски для VM
  ├─ Object Storage: S3 (AWS), Blob (Azure) — хранение файлов, backups, data lakes
  ├─ File Storage: EFS (AWS), Azure Files — сетевые файловые системы
  └─ Архивное: Glacier (AWS) — холодное хранение (редкий доступ, дешёвое)

• ОРКЕСТРАЦИЯ И АВТОМАТИЗАЦИЯ:

  INFRASTRUCTURE AS CODE (IaC):
  ├─ Terraform: декларативное описание инфраструктуры (multi-cloud)
  ├─ CloudFormation (AWS), ARM Templates (Azure): нативные IaC
  ├─ Ansible, Puppet, Chef: configuration management
  └─ Преимущества: версионирование, repeatability, disaster recovery

  Пример Terraform:
  ```hcl
  resource "aws_instance" "web" {
    ami           = "ami-12345"
    instance_type = "t3.medium"
    count         = 3
  }
  ```
  → создаст 3 идентичных инстанса

  KUBERNETES (K8s) — оркестрация контейнеров:
  ├─ Автоматическое масштабирование: добавление/удаление pods
  ├─ Service discovery: автоматическое нахождение сервисов
  ├─ Self-healing: перезапуск упавших контейнеров
  ├─ Rolling updates: обновление без downtime
  └─ Managed K8s: EKS (AWS), AKS (Azure), GKE (Google)

  CI/CD PIPELINES:
  ├─ GitHub Actions, GitLab CI, Jenkins
  ├─ Автоматическое тестирование, сборка, деплой
  ├─ Blue-Green deployments: zero downtime
  └─ Canary releases: постепенный раскат новых версий

• ГЛОБАЛЬНАЯ ИНФРАСТРУКТУРА:

  REGIONS И AVAILABILITY ZONES:
  ├─ Region: географическая зона (us-east-1, eu-west-1)
  │  └─ Выбор: latency, compliance, data residency
  ├─ Availability Zone (AZ): изолированный дата-центр внутри региона
  │  └─ AWS: обычно 3-6 AZ на регион
  └─ Архитектура: multi-AZ для высокой доступности (HA)

  Пример multi-AZ:
  - Load Balancer в нескольких AZ
  - Application servers в разных AZ
  - Database: primary в AZ-1, standby в AZ-2
  - ЕСЛИ AZ-1 падает → automatic failover на AZ-2

  CONTENT DELIVERY NETWORK (CDN):
  ├─ CloudFront (AWS), Azure CDN, Cloudflare
  ├─ Кэширование статики на edge locations (сотни точек по миру)
  ├─ Уменьшение latency: контент ближе к пользователю
  └─ Разгрузка origin server

  DISASTER RECOVERY:
  ├─ Multi-region: критичные приложения в нескольких регионах
  ├─ Backups: кросс-региональная репликация
  ├─ RTO/RPO: Recovery Time/Point Objective
  └─ Chaos Engineering: проактивное тестирование отказов

• MANAGED SERVICES — ключевое преимущество облака:

  COMPUTE:
  ├─ EC2 (AWS), VMs (Azure): виртуальные серверы
  ├─ Lambda (AWS), Azure Functions: serverless функции
  ├─ Fargate (AWS), Container Instances (Azure): serverless контейнеры
  └─ Batch processing: автоматические вычислительные задачи

  DATABASES:
  ├─ RDS (AWS): managed PostgreSQL, MySQL, Oracle, SQL Server
  │  └─ Автоматические backups, patching, scaling
  ├─ DynamoDB (AWS), Cosmos DB (Azure): NoSQL, fully managed
  ├─ Aurora (AWS): MySQL/PostgreSQL-compatible, cloud-native
  └─ Redshift (AWS): data warehouse (аналитика)

  AI/ML:
  ├─ SageMaker (AWS): end-to-end ML platform
  ├─ Rekognition (AWS): computer vision API
  ├─ Comprehend (AWS): NLP (анализ текста)
  └─ OpenAI API, Azure OpenAI: GPT-4, DALL-E

  ANALYTICS:
  ├─ Athena (AWS): SQL queries на S3 (serverless)
  ├─ BigQuery (Google): data warehouse
  ├─ EMR (AWS): Hadoop/Spark clusters
  └─ Streaming: Kinesis (AWS), Event Hubs (Azure)

  SECURITY:
  ├─ IAM: управление доступом (users, roles, policies)
  ├─ KMS: управление ключами шифрования
  ├─ GuardDuty (AWS): threat detection
  └─ Security Hub: централизованный security dashboard

• ЭКОНОМИКА ОБЛАКА:

  PAY-AS-YOU-GO:
  ├─ Почасовая оплата: платишь только когда работает
  ├─ Autoscaling: экономия в нерабочее время
  └─ Spot instances: аукцион на неиспользуемые мощности (до 90% скидка)

  RESERVED INSTANCES / SAVINGS PLANS:
  ├─ Обязательство на 1-3 года
  ├─ Скидки: 30-70% от on-demand
  └─ Для предсказуемых рабочих нагрузок

  FREE TIER:
  ├─ AWS: 750 часов EC2 t2.micro/месяц (первый год)
  ├─ Azure: $200 кредитов (первый месяц)
  └─ GCP: $300 кредитов (90 дней)

  COST OPTIMIZATION:
  ├─ Right-sizing: выбор правильного размера инстанса
  ├─ Unused resources: удаление неиспользуемых (orphaned volumes, IPs)
  ├─ Reserved capacity: для постоянных рабочих нагрузок
  ├─ Spot instances: для fault-tolerant workloads
  └─ Cost monitoring: CloudWatch, Cost Explorer, third-party (CloudHealth)

• ПРОБЛЕМЫ И ОГРАНИЧЕНИЯ:

  VENDOR LOCK-IN:
  ├─ Проприетарные сервисы: S3, DynamoDB, Lambda — специфичны для AWS
  ├─ Миграция на другой облако: дорого, сложно
  ├─ Зависимость: провайдер повышает цены → нет альтернативы
  └─ Решение: multi-cloud стратегия, использование open-source (Kubernetes, Postgres)

  СЛОЖНОСТЬ:
  ├─ Сотни сервисов: AWS >200 сервисов
  ├─ Обучение: нужна экспертиза (AWS Certified, Azure Certified)
  ├─ Billing: сложность понимания счетов (множество компонентов)
  └─ Overprovisioning: "на всякий случай" → переплата

  SECURITY И COMPLIANCE:
  ├─ Shared Responsibility Model:
  │  ├─ Провайдер: безопасность инфраструктуры (physical, network, hypervisor)
  │  └─ Клиент: безопасность в облаке (OS patching, data, IAM, encryption)
  ├─ Data residency: где физически хранятся данные (GDPR, российские законы)
  ├─ Compliance: HIPAA (медицина), PCI DSS (платёжные карты), FedRAMP (гос)
  └─ Ошибки конфигурации: S3 buckets открыты публично → утечки

  LATENCY:
  ├─ Физическое расстояние до дата-центра
  ├─ Интернет-зависимость: нет интернета → нет доступа к облаку
  └─ Для real-time приложений: on-premise может быть лучше

  СТОИМОСТЬ:
  ├─ Может быть дороже on-premise для постоянных, предсказуемых нагрузок
  ├─ Data transfer: egress traffic дорогой (выход из облака)
  ├─ "Cloud sprawl": неконтролируемое создание ресурсов
  └─ Repatriation: некоторые компании возвращаются on-premise (Dropbox, 37signals)

АЛГОРИТМ МИГРАЦИИ В ОБЛАКО (Cloud Migration)

Шаг 1: ОЦЕНКА И ПЛАНИРОВАНИЕ (Assessment)

INVENTORY АКТИВОВ:
├─ Список всех приложений, сервисов, баз данных
├─ Зависимости: какие приложения связаны друг с другом
├─ Текущие характеристики:
│  ├─ Compute: CPU, RAM, storage
│  ├─ Network: bandwidth, latency requirements
│  └─ Performance: метрики использования
└─ Compliance требования: где должны храниться данные

БИЗНЕС-КЕЙС:
├─ Зачем мигрировать? (cost savings, agility, innovation, disaster recovery)
├─ TCO анализ: Total Cost of Ownership
│  ├─ On-premise: hardware, электричество, охлаждение, зарплаты, лицензии
│  └─ Cloud: pay-as-you-go, reserved instances, managed services
├─ ROI: Return on Investment (сколько сэкономим/заработаем)
└─ Риски: downtime, data loss, security breaches

6 R's СТРАТЕГИИ МИГРАЦИИ:
├─ Rehost (Lift-and-shift): перенос как есть, без изменений
│  └─ Быстро, но не использует преимущества облака
├─ Replatform (Lift-and-reshape): минимальные изменения для оптимизации
│  └─ Пример: VM → managed database
├─ Repurchase: замена на SaaS
│  └─ Пример: свой email server → Google Workspace
├─ Refactor/Re-architect: переписать для облака (cloud-native)
│  └─ Долго, дорого, но максимальная выгода
├─ Retire: удалить неиспользуемые приложения
└─ Retain: оставить on-premise (compliance, latency)

ВЫБОР ПРОВАЙДЕРА:
├─ AWS: лидер рынка, максимум сервисов
├─ Azure: интеграция с Microsoft ecosystem
├─ GCP: сильны в data/AI
├─ Multi-cloud: несколько провайдеров (избежать lock-in, но сложность)
└─ Критерии: цена, регионы, сервисы, поддержка, compliance

Шаг 2: PROOF OF CONCEPT (PoC)

ПИЛОТНЫЙ ПРОЕКТ:
├─ Выбрать небольшое, некритичное приложение
├─ Мигрировать в облако
├─ Тестировать: функциональность, производительность, cost
├─ Обучение команды: hands-on опыт
└─ ЕСЛИ PoC успешен → масштабировать на другие приложения

LANDING ZONE (базовая инфраструктура):
├─ Account structure: организационные единицы, множественные аккаунты
├─ VPC: сетевая архитектура (subnets, routing)
├─ IAM: роли, политики доступа
├─ Security: GuardDuty, Security Hub, Config
├─ Logging: CloudTrail, CloudWatch
└─ Billing: Cost Explorer, budgets, alerts

Шаг 3: МИГРАЦИЯ ДАННЫХ

DATA TRANSFER:
├─ Для малых объёмов (<10 TB):
│  └─ Сетевая передача: Direct Connect, VPN, интернет
├─ Для больших объёмов (>10 TB):
│  └─ Physical transfer: AWS Snowball, Azure Data Box (шифрованные диски)
├─ Для огромных (>100 PB):
│  └─ AWS Snowmobile (грузовик с контейнером!)
└─ Database Migration Service (DMS): онлайн миграция БД с минимальным downtime

SYNCHRONIZATION:
├─ Первичная репликация: полная копия данных
├─ Change Data Capture (CDC): синхронизация изменений в реальном времени
├─ Cutover: переключение production на облако
└─ Rollback план: на случай проблем

Шаг 4: МИГРАЦИЯ ПРИЛОЖЕНИЙ

REHOST (Lift-and-shift):
├─ Создать VM images (AMIs на AWS)
├─ Запустить EC2 instances
├─ Настроить networking, security groups
├─ Тестирование
└─ Cutover: переключить DNS на облачные IP

CONTAINERIZATION (для modernization):
├─ Создать Docker images
├─ Настроить Kubernetes cluster (EKS, AKS, GKE)
├─ Deploy приложения как pods
├─ Service mesh: Istio для управления трафиком
└─ Monitoring: Prometheus, Grafana

SERVERLESS (для функциональности):
├─ Разбить приложение на функции
├─ Написать Lambda functions (или Azure Functions)
├─ API Gateway для HTTP endpoints
├─ Event-driven: триггеры на события (S3, DynamoDB, SQS)
└─ Статика: S3 + CloudFront

Шаг 5: ТЕСТИРОВАНИЕ

FUNCTIONAL TESTING:
├─ Все features работают корректно?
├─ Интеграции с другими системами?
└─ User Acceptance Testing (UAT)

PERFORMANCE TESTING:
├─ Load testing: выдерживает ли нагрузку?
├─ Stress testing: точка отказа
├─ Latency: задержки в приемлемых пределах?
└─ Инструменты: JMeter, Gatling, Locust

SECURITY TESTING:
├─ Penetration testing
├─ Vulnerability scanning
├─ Compliance проверка
└─ IAM: правильные права доступа?

DISASTER RECOVERY TESTING:
├─ Failover: переключение на standby
├─ Backup restore: восстановление из бэкапа
└─ RTO/RPO: соответствуют ли требованиям?

Шаг 6: CUTOVER (Переключение)

ПЛАНИРОВАНИЕ CUTOVER:
├─ Выбор окна: минимальная нагрузка (ночь, выходные)
├─ Communication: уведомление пользователей
├─ Rollback plan: на случай провала
└─ Checklist: всё ли готово?

EXECUTION:
├─ Freeze on-premise: остановить изменения
├─ Финальная синхронизация данных
├─ DNS переключение: направить трафик на облако
├─ Мониторинг: отслеживать метрики, логи, ошибки
└─ ЕСЛИ проблемы → rollback на on-premise

POST-CUTOVER:
├─ Hypercare period: повышенный мониторинг (1-2 недели)
├─ Оптимизация: right-sizing instances, cost optimization
└─ Decommission on-premise: после уверенности в стабильности

Шаг 7: ОПТИМИЗАЦИЯ И GOVERNANCE

COST OPTIMIZATION:
├─ Анализ использования: неиспользуемые ресурсы?
├─ Right-sizing: слишком большие instances?
├─ Reserved instances: для предсказуемых нагрузок
├─ Autoscaling: динамическое масштабирование
└─ Spot instances: для non-critical workloads

WELL-ARCHITECTED FRAMEWORK (AWS):
├─ Operational Excellence: автоматизация, мониторинг
├─ Security: IAM, encryption, compliance
├─ Reliability: multi-AZ, backups, disaster recovery
├─ Performance Efficiency: right-sizing, caching, CDN
├─ Cost Optimization: pay-as-you-go, reserved capacity
└─ Sustainability: энергоэффективность

GOVERNANCE:
├─ Tagging: организация ресурсов (project, environment, owner)
├─ Policies: что разрешено создавать (Service Control Policies)
├─ Budgets: алерты на превышение
└─ Compliance: continuous auditing (AWS Config, Azure Policy)

Шаг 8: CONTINUOUS IMPROVEMENT

МОНИТОРИНГ:
├─ CloudWatch, Azure Monitor: метрики, логи, алерты
├─ APM: Application Performance Monitoring (Datadog, New Relic)
├─ Cost monitoring: детализация трат
└─ Security: continuous vulnerability scanning

AUTOMATION:
├─ IaC: всё в коде (Terraform, CloudFormation)
├─ CI/CD: автоматический деплой
├─ Auto-remediation: автоматическое исправление проблем
└─ ChatOps: управление через Slack/Teams

INNOVATION:
├─ Использование managed services: меньше undifferentiated heavy lifting
├─ AI/ML: внедрение ML моделей
├─ Serverless: где возможно
└─ Experimentation: A/B testing, canary deployments

КОНТЕКСТ И ПРОИСХОЖДЕНИЕ

Две противоположные точки зрения на облако:

ОПТИМИСТЫ: "Облако = утилита"
- Как электричество: подключился, платишь за потребление
- Не нужно строить свою электростанцию (дата-центр)
- Демократизация: стартапы получают доступ к enterprise инфраструктуре
- Фокус на бизнесе, а не на инфраструктуре

СКЕПТИКИ: "Облако = чужой компьютер"
- Потеря контроля: данные на чужих серверах
- Зависимость от провайдера: что если AWS падает? Или повышает цены?
- Security concerns: доверяете ли Amazon/Microsoft свои данные?
- Vendor lock-in: миграция обратно = очень дорого

Реальность: обе точки зрения верны, зависит от контекста

ПРИМЕРЫ ПРИМЕНЕНИЯ

ПРИМЕР 1: Netflix — облачный гигант

МИГРАЦИЯ:
• 2008-2016: полная миграция в AWS (8 лет!)
• Зачем: собственные дата-центры не успевали за ростом
• 100% в облаке: нет on-premise инфраструктуры

АРХИТЕКТУРА:
• Microservices: сотни сервисов, независимое масштабирование
• Auto-scaling: миллионы пользователей вечером → масштабирование вверх
                ночью → масштабирование вниз
• Multi-region: disaster recovery, low latency globally
• Chaos Engineering: Netflix Simian Army (Chaos Monkey)
  └─ Специально "ломают" части системы, чтобы проверить resilience

РЕЗУЛЬТАТЫ:
✓ Глобальное масштабирование: 200+ млн подписчиков
✓ 99.99% availability
✓ Быстрый запуск в новых странах (без строительства дата-центров)
✓ Innovation: focus на контент и UX, а не на инфраструктуру

ПРОБЛЕМЫ:
✗ Vendor lock-in: полностью зависят от AWS
✗ Cost: миллиарды долларов на AWS (но альтернатива дороже)
✗ 2021: "Мы рассматриваем multi-cloud" (но миграция огромна)

УРОК: Для масштабных, глобальных приложений облако = enabler роста

ПРИМЕР 2: Capital One — bank в облаке

МИГРАЦИЯ:
• Традиционный банк, on-premise дата-центры
• 2015: решение мигрировать в AWS (один из первых крупных банков)
• 2020: закрыли последние дата-центры, 100% в облаке

МОТИВАЦИЯ:
• Agility: запуск новых features за недели vs месяцы
• Security: AWS инвестирует больше в security, чем банк может
• Compliance: AWS FedRAMP, PCI DSS сертифицированы
• Innovation: ML, AI для fraud detection, personalization

РЕЗУЛЬТАТЫ:
✓ Быстрый выпуск новых продуктов
✓ Cost savings: оптимизация, autoscaling
✓ Improved security posture (по их заявлениям)

НО: 2019 — DATA BREACH!
✗ 100 млн клиентских records украдены
✗ Причина: S3 bucket был открыт публично (misconfiguration)
✗ Не вина AWS, а ошибка инженера Capital One
✗ $80 млн штрафа, репутационный урон

УРОК: Облако не делает вас автоматически безопасными
       Shared Responsibility Model: клиент ответственен за конфигурацию

ПРИМЕР 3: Dropbox — repatriation (возврат из облака)

ИСТОРИЯ:
• 2007-2016: Dropbox использовал AWS S3 для хранения файлов
• 2016: объявили переход на собственную инфраструктуру "Magic Pocket"
• 2018: миграция завершена, 90%+ данных на собственных серверах

ПОЧЕМУ УШЛИ ИЗ ОБЛАКА:
• Масштаб: exabytes данных → AWS S3 стоил сотни миллионов $/год
• Предсказуемая нагрузка: storage постоянно растёт (не спайки)
• Экономика: собственные дата-центры дешевле для их use case
• Control: оптимизация storage специфично для их workload

РЕЗУЛЬТАТЫ:
✓ Экономия: $75 млн за 2 года (2016-2017)
✓ Performance: оптимизация под свои нужды
✓ Retention: продолжают использовать AWS для edge cases, compute

НО:
✗ Огромные upfront инвестиции: дата-центры, hardware, персонал
✗ Сложность: управление инфраструктурой отвлекает от продукта
✗ Не для всех: работает для Dropbox, не для большинства компаний

УРОК: Облако не всегда дешевле
       Для predictable, massive workloads on-premise может быть выгоднее

ПРИМЕР 4: AWS Outages — когда облако падает

ИНЦИДЕНТЫ:
• 2017: S3 outage в us-east-1 (4 часа)
  └─ Typo в команде: инженер случайно выключил больше серверов, чем планировал
  └─ Последствия: половина интернета не работала (Slack, Trello, Quora, др.)

• 2021: AWS outage в us-east-1 (несколько часов)
  └─ Проблема с network devices
  └─ Жертвы: Disney+, Robinhood, Coinbase, даже сам AWS console не работал

• 2022: Azure outage (глобальная)
  └─ DDoS атака + проблема в DDoS mitigation
  └─ Microsoft services (Teams, Outlook, Azure) не работали

ПРОБЛЕМА:
• Single point of failure: us-east-1 = крупнейший регион AWS
• Cascading failures: сбой одного сервиса → влияет на другие
• Lack of multi-region: многие компании в одном регионе (проще, дешевле)

УРОК: Облако не = 100% uptime
       Multi-region, multi-cloud для критичных приложений
       "Don't put all eggs in one basket"

СВЯЗЬ С ФОРМУЛОЙ

Cloud Value = (Scalability + Availability + Flexibility) / (CapEx + OpEx)

- Netflix: высокая Scalability/Flexibility → высокая Value
- Dropbox: высокая OpEx (AWS дорого для их scale) → низкая Value → repatriation
- Capital One: CapEx→OpEx, но Security misconfiguration снизила Value

IaaS vs PaaS vs SaaS:
- Больше контроля (IaaS) = больше ответственности (security, patching)
- Меньше контроля (SaaS) = меньше гибкости, но проще

ПРАКТИЧЕСКИЕ СОВЕТЫ

1. НАЧИНАТЬ С МАЛОГО
   ✓ PoC на некритичном приложении
   ✓ Обучение команды
   ✓ Постепенное масштабирование

2. MULTI-AZ / MULTI-REGION
   ✓ Для критичных: минимум multi-AZ
   ✓ Для крайне критичных: multi-region
   ✓ Тестировать failover регулярно

3. COST OPTIMIZATION С НАЧАЛА
   ✓ Tagging ресурсов
   ✓ Budgets и алерты
   ✓ Right-sizing, autoscaling
   ✓ Spot instances где возможно

4. SECURITY — ПРИОРИТЕТ #1
   ✓ Least privilege IAM
   ✓ Encryption at rest and in transit
   ✓ Security groups: minimal open ports
   ✓ Regular audits, penetration testing

5. INFRASTRUCTURE AS CODE
   ✓ Terraform, CloudFormation
   ✓ Version control (Git)
   ✓ Peer review для изменений
   ✓ Disaster recovery: rebuild from code

6. ИЗБЕГАТЬ VENDOR LOCK-IN
   ✓ Использовать open-source где возможно (Kubernetes, Postgres)
   ✓ Abstraction layers
   ✓ Multi-cloud для критичного

7. МОНИТОРИНГ И АЛЕРТЫ
   ✓ CloudWatch, Datadog, New Relic
   ✓ Алерты на аномалии
   ✓ Dashboards для visibility
