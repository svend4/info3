C = A + D + T

где:
C (Code Quality) — качество кода
A (Algorithms) — алгоритмы и структуры данных
D (Design) — архитектура, дизайн
T (Testing) — тестирование

Альтернативная формула продуктивности разработки:

P = S × (1 - B) × M

где:
P (Productivity) — продуктивность
S (Skill) — навык программирования
B (Bugs density) — плотность багов (0-1, чем меньше, тем лучше)
M (Maintainability) — поддерживаемость кода

АРХЕТИП КАЧЕСТВЕННОГО КОДА

Хороший код = (Читаемость × Работоспособность × Эффективность) ×
              (Тестируемость + Модульность) ÷
              (Сложность + Дублирование + Технический долг) +
              Документация

где компоненты детализированы:

• Читаемость (Readability):
  - Код пишется один раз, читается сотни раз
  - Понятные имена переменных, функций (не x, a1, tmp)
  - Последовательный стиль (форматирование, отступы)
  - Комментарии: НЕ "что делает", а "почему делает"
  - "Код должен читаться как проза" (Clean Code, Роберт Мартин)

• Работоспособность (Correctness):
  - Код делает то, что должен (без багов)
  - Обрабатывает граничные случаи (пустой ввод, null, переполнение)
  - Graceful degradation: корректное поведение при ошибках
  - "Сначала сделай работающим, потом быстрым, потом красивым"

• Эффективность (Efficiency):
  - Временная сложность: O(n) vs O(n²) vs O(log n)
  - Пространственная сложность: использование памяти
  - НО: преждевременная оптимизация = корень зла (Кнут)
  - Оптимизировать только узкие места (bottlenecks)

• Тестируемость (Testability):
  - Код легко покрыть тестами
  - Функции делают одно (Single Responsibility)
  - Инъекция зависимостей (не hardcode)
  - TDD: Test-Driven Development (тесты сначала, код потом)

• Модульность (Modularity):
  - Разбиение на независимые модули
  - Слабая связанность (loose coupling)
  - Высокая связность (high cohesion)
  - Принцип единственной ответственности (SRP)

• Сложность (Complexity) — враг:
  - Цикломатическая сложность (количество путей в коде)
  - Вложенность (if в if в if → рефакторить)
  - "Любой дурак может написать код, понятный компьютеру. 
    Хорошие программисты пишут код, понятный людям" (Фаулер)

• Дублирование (Duplication) — враг:
  - DRY: Don't Repeat Yourself
  - Copy-paste = источник багов (изменили одно место, забыли другое)
  - Вынести в функцию/класс

• Технический долг (Technical Debt):
  - "Быстрые и грязные" решения → накапливаются
  - Со временем: замедление разработки, больше багов
  - Нужно периодически рефакторить (погашать долг)

• Документация (Documentation):
  - README: как запустить, что делает проект
  - API documentation: как использовать функции/классы
  - Inline comments: почему (не что)
  - Примеры использования

Принципы программирования:

SOLID (объектно-ориентированное программирование):
├─ S: Single Responsibility — один класс = одна ответственность
├─ O: Open/Closed — открыт для расширения, закрыт для изменения
├─ L: Liskov Substitution — подклассы заменяют базовые классы
├─ I: Interface Segregation — много специфичных интерфейсов > один общий
└─ D: Dependency Inversion — зависеть от абстракций, не от конкретики

KISS: Keep It Simple, Stupid
├─ Простота > сложность
├─ Не усложнять без необходимости
└─ "Делай проще, тупица"

YAGNI: You Aren't Gonna Need It
├─ Не добавляй функциональность "на будущее"
├─ Пиши только то, что нужно сейчас
└─ Избегай over-engineering

АЛГОРИТМ РАЗРАБОТКИ КАЧЕСТВЕННОГО ПО

Шаг 1: ПОНИМАНИЕ ЗАДАЧИ

ТРЕБОВАНИЯ:
├─ Что нужно сделать? (функциональные требования)
├─ Как должно работать? (нефункциональные: производительность, безопасность)
├─ Кто пользователи? (UX, интерфейс)
├─ Ограничения? (бюджет, время, технологии)
└─ ЕСЛИ требования неясны
   └─ ТО задавать вопросы, уточнять (не начинать кодить сразу!)

РАЗБИЕНИЕ НА ЗАДАЧИ:
├─ Большая задача → подзадачи (декомпозиция)
├─ Использовать: User Stories, Use Cases
├─ Оценка времени: реалистичная (умножить на π, если неуверен)
└─ Приоритизация: что критично, что можно отложить

Шаг 2: ПРОЕКТИРОВАНИЕ (Design)

АРХИТЕКТУРА:
├─ Какие компоненты/модули?
├─ Как они взаимодействуют?
├─ Паттерны проектирования: MVC, Observer, Factory, Singleton, и др.
├─ База данных: схема, отношения
└─ API: какие эндпоинты, форматы данных (REST, GraphQL)

ВЫБОР ТЕХНОЛОГИЙ:
├─ Язык программирования: Python, JavaScript, Java, C++, Rust?
├─ Фреймворки: React, Django, Spring, Express?
├─ База данных: PostgreSQL, MongoDB, Redis?
├─ Облако: AWS, Google Cloud, Azure?
└─ ЕСЛИ знакомая технология vs новая модная
   └─ ТО чаще выбирать знакомую (меньше риска)

ДИАГРАММЫ:
├─ UML: классы, последовательности, компоненты
├─ Схемы БД: ER-диаграммы
├─ Flowcharts: логика алгоритмов
└─ НЕ обязательно, но полезно для сложных систем

Шаг 3: НАПИСАНИЕ КОДА (Implementation)

НАСТРОЙКА ОКРУЖЕНИЯ:
├─ Установка языка, фреймворков
├─ IDE/редактор: VS Code, PyCharm, Vim
├─ Виртуальные окружения: venv, conda, Docker
├─ Система контроля версий: Git + GitHub/GitLab
└─ Линтеры: eslint, pylint, black (автоформатирование)

TDD (Test-Driven Development) — опционально, но рекомендуется:
├─ Шаг 1: Написать тест (он упадёт, т.к. функции нет)
├─ Шаг 2: Написать минимальный код, чтобы тест прошёл
├─ Шаг 3: Рефакторинг (улучшить код, тесты остаются зелёными)
└─ Повторить для каждой функции

CODING:
├─ Начать с простого (MVP: Minimum Viable Product)
├─ Инкрементальная разработка (маленькими шагами)
├─ Частые коммиты в Git (не один большой в конце)
├─ Понятные commit messages: "Добавлена функция X", а не "fix"
├─ Code review: коллеги проверяют код (находят баги, улучшают качество)
└─ ЕСЛИ застрял > 30 минут
   └─ ТО попросить помощи (Stack Overflow, коллеги, ChatGPT)

ПРИНЦИПЫ НАПИСАНИЯ:
├─ Читаемость: имена переменных = понятные (user_age, а не ua)
├─ Функции: маленькие (5-20 строк), делают одно
├─ Классы: Single Responsibility
├─ DRY: не дублировать код
├─ KISS: простота
└─ YAGNI: не усложнять

Шаг 4: ТЕСТИРОВАНИЕ (Testing)

ВИДЫ ТЕСТОВ:
├─ Unit tests: тестируют отдельные функции/классы
│  └─ Быстрые, много (сотни/тысячи)
├─ Integration tests: тестируют взаимодействие модулей
│  └─ Средние по скорости, меньше (десятки)
├─ End-to-end tests: тестируют систему целиком (как пользователь)
│  └─ Медленные, мало (единицы)
└─ Пирамида тестирования: много unit, меньше integration, мало e2e

COVERAGE:
├─ Измерить покрытие кода тестами (code coverage)
├─ Цель: 70-90% (100% не обязательно, но критичные части = 100%)
└─ ЕСЛИ coverage низкий → добавить тесты

АВТОМАТИЗАЦИЯ:
├─ CI/CD: Continuous Integration/Continuous Deployment
├─ GitHub Actions, GitLab CI, Jenkins
├─ При каждом commit → автоматически запускаются тесты
├─ ЕСЛИ тесты упали → commit отклонён (не попадает в main)
└─ Автоматический деплой после успешных тестов

РУЧНОЕ ТЕСТИРОВАНИЕ:
├─ QA инженеры тестируют вручную
├─ Проверяют UX, граничные случаи
├─ Находят баги, которые автотесты пропустили
└─ Важно для UI/UX

Шаг 5: РЕФАКТОРИНГ (Refactoring)

КОГДА:
├─ Код работает, но выглядит плохо (спагетти-код)
├─ Появились дубликаты
├─ Функции стали большими (> 50 строк)
├─ Сложность выросла (трудно понять логику)
└─ Технический долг накопился

КАК:
├─ Выделить функцию (Extract Method)
├─ Переименовать переменные (Rename)
├─ Убрать дубликаты (DRY)
├─ Упростить условия (Replace nested conditional with guard clauses)
├─ Паттерны проектирования (если подходят)
└─ ВАЖНО: после рефакторинга тесты должны оставаться зелёными!

ПРАВИЛО:
├─ "Оставь код лучше, чем нашёл" (Boy Scout Rule)
├─ Каждый раз, работая с файлом, немного улучшай его
└─ Постепенное улучшение > большой рефакторинг раз в год

Шаг 6: CODE REVIEW

ЗАЧЕМ:
├─ Найти баги до продакшена
├─ Улучшить качество кода (коллеги предлагают улучшения)
├─ Обмен знаниями (учиться друг у друга)
└─ Консистентность стиля в команде

КАК:
├─ Pull Request (PR) в GitHub/GitLab
├─ Коллеги читают код, оставляют комментарии
├─ Автор отвечает, вносит изменения
├─ ЕСЛИ одобрено → merge в main branch
└─ Культура: конструктивная критика, не личные нападки

ЧТО ПРОВЕРЯТЬ:
├─ Логика: правильно ли работает?
├─ Читаемость: понятен ли код?
├─ Тесты: покрыты ли новые функции?
├─ Безопасность: нет ли уязвимостей (SQL injection, XSS)?
├─ Производительность: нет ли узких мест?
└─ Стиль: соответствует ли code style проекта?

Шаг 7: ДЕПЛОЙ (Deployment)

ОКРУЖЕНИЯ:
├─ Development (dev): локальная разработка
├─ Staging: копия продакшена для финальных тестов
├─ Production (prod): реальные пользователи
└─ НЕ деплоить прямо в prod (сначала staging!)

CI/CD PIPELINE:
├─ Commit → тесты → build → staging → тесты на staging → prod
├─ Автоматизация: одна команда/кнопка → деплой
├─ Rollback: если что-то сломалось, откатить назад
└─ Blue-Green deployment: два prod окружения, переключение без даунтайма

МОНИТОРИНГ:
├─ Логирование: записывать события, ошибки
├─ Метрики: производительность (latency, throughput, error rate)
├─ Алерты: уведомления при ошибках (PagerDuty, Slack)
└─ Dashboards: визуализация метрик (Grafana, Datadog)

Шаг 8: ПОДДЕРЖКА И ИТЕРАЦИИ (Maintenance)

БАГИ В ПРОДАКШЕНЕ:
├─ Пользователи сообщают о багах
├─ Приоритизация: critical (чинить сразу) vs low (в следующем спринте)
├─ Hotfix: срочное исправление → деплой
└─ Post-mortem: анализ причины, как избежать в будущем

НОВЫЕ ФИЧИ:
├─ Обратная связь от пользователей
├─ Product roadmap: что делать дальше
├─ Итерации: добавлять функции постепенно
└─ Agile/Scrum: спринты (2 недели), демо, ретроспективы

ТЕХНИЧЕСКИЙ ДОЛГ:
├─ Выделять время на рефакторинг (не только новые фичи)
├─ "20% времени на технический долг" — хорошая практика
└─ Баланс: новые фичи vs качество кода

ТЕОРЕМА: "Код пишется один раз, читается сотни раз"

КОНТЕКСТ И ПРОИСХОЖДЕНИЕ

Фундаментальный принцип разработки ПО, подчёркивающий важность читаемости кода.

Авторство приписывается разным людям (Мартин Фаулер, Роберт Мартин), но идея
древняя и общепризнанная в индустрии.

Суть:
- Время написания кода: несколько минут/часов
- Время чтения кода: каждый раз, когда нужно понять, изменить, отладить
- Разработчики тратят 90% времени на ЧТЕНИЕ кода, 10% на написание

Следствие: оптимизировать код для ЧТЕНИЯ, а не для СКОРОСТИ НАПИСАНИЯ.

ОБЪЯСНЕНИЕ

Почему читаемость критична:

1. КОД ЖИВЁТ ДОЛГО

   Типичная ситуация:
   - Написал код сегодня
   - Через 6 месяцев: нужно добавить фичу или исправить баг
   - Открываешь файл: "Что это? Кто это написал? О, это я... но я не помню!"
   
   Если код нечитаемый:
   - Тратишь часы на понимание
   - Риск сломать что-то при изменении (не понимаешь, как работает)
   - Фрустрация, замедление разработки
   
   Если код читаемый:
   - Понимание за минуты
   - Уверенные изменения
   - Радость от работы

2. КОД ЧИТАЮТ ДРУГИЕ (И БУДУЩИЙ ТЫ)

   Код не только для компилятора:
   - Коллеги будут читать (code review, совместная работа)
   - Новые разработчики (onboarding)
   - Ты сам через время (будущий ты = другой человек)
   
   Читаемый код = уважение к другим (и к себе будущему).

3. ЧТЕНИЕ ≠ НАПИСАНИЕ

   Написание: линейный процесс (сверху вниз)
   Чтение: нелинейный (прыгаешь между функциями, файлами, ищешь логику)
   
   Оптимизация для чтения:
   - Понятные имена (не нужно гадать, что делает)
   - Маленькие функции (легко держать в голове)
   - Комментарии для неочевидных мест
   - Последовательная структура

4. "УМНЫЙ" КОД = ПЛОХОЙ КОД

   Соблазн:
   - Написать "умный" однострочник, использовать obscure features языка
   - Цель: показать мастерство, сократить код
   
   Проблема:
   - Другие (и ты через время) не поймут
   - Debugging кошмарен
   - "Умный" код часто = багги код
   
   Правильно:
   - Простота > умность
   - Явность > неявность
   - Многословность (если нужна) > краткость в ущерб ясности

5. СТОИМОСТЬ НЕЧИТАЕМОГО КОДА

   Финансовая:
   - Больше времени на понимание → больше зарплатных расходов
   - Больше багов → больше времени на исправления
   - Медленная разработка → позже релиз → упущенная прибыль
   
   Человеческая:
   - Фрустрация разработчиков
   - Выгорание (работа с плохим кодом = стресс)
   - Текучка кадров (люди уходят из проектов с legacy спагетти-кодом)

ПРИМЕРЫ ПРИМЕНЕНИЯ

ПРИМЕР 1: Имена переменных

ПЛОХО (нечитаемо):
```python
def f(x, y):
    t = x * y
    if t > 100:
        return t * 1.1
    return t
```

Что это делает? Нужно анализировать логику.

ХОРОШО (читаемо):
```python
def calculate_order_total_with_discount(price, quantity):
    total = price * quantity
    if total > 100:
        # Apply 10% discount for orders over $100
        return total * 1.1
    return total
```

Сразу понятно: вычисляет итог заказа с скидкой.

УРОК: Имена = документация. Понятное имя экономит часы чтения.

ПРИМЕР 2: Функция делает ОДНО

ПЛОХО (спагетти, делает всё):
```python
def process_user(user_id):
    # Fetch user from database
    user = db.query(f"SELECT * FROM users WHERE id={user_id}")
    # Validate email
    if '@' not in user['email']:
        raise ValueError("Invalid email")
    # Send welcome email
    smtp.send(user['email'], "Welcome!")
    # Update last_login
    db.query(f"UPDATE users SET last_login=NOW() WHERE id={user_id}")
    # Log activity
    logger.info(f"User {user_id} processed")
    return user
```

Проблемы:
- Делает 5 вещей (fetch, validate, send email, update, log)
- Тяжело тестировать
- Если нужно изменить логику email → нужно понять всю функцию

ХОРОШО (разбито на функции):
```python
def get_user(user_id):
    return db.query(f"SELECT * FROM users WHERE id={user_id}")

def validate_user_email(user):
    if '@' not in user['email']:
        raise ValueError("Invalid email")

def send_welcome_email(user):
    smtp.send(user['email'], "Welcome!")

def update_last_login(user_id):
    db.query(f"UPDATE users SET last_login=NOW() WHERE id={user_id}")

def process_user(user_id):
    user = get_user(user_id)
    validate_user_email(user)
    send_welcome_email(user)
    update_last_login(user_id)
    logger.info(f"User {user_id} processed")
    return user
```

Преимущества:
- Каждая функция = одно действие (понятно, что делает)
- Легко тестировать отдельно
- Легко изменять (хочешь изменить email → меняешь только send_welcome_email)
- process_user читается как инструкция

УРОК: Single Responsibility = читаемость + тестируемость.

ПРИМЕР 3: Комментарии (когда и как)

ПЛОХО (бесполезные комментарии):
```python
# Increment i
i = i + 1

# Check if user is admin
if user.role == 'admin':
    # Allow access
```

ПРИМЕР 4: Legacy код (реальная боль)

СИТУАЦИЯ:
• Компания 10 лет, проект писали разные люди
• Код: 100,000 строк, нет тестов, имена переменных = x1, tmp, data
• Новый разработчик: задача добавить фичу

ПРОБЛЕМА:
• Неделя уходит на ПОНИМАНИЕ кода (не на написание!)
• Страх что-то сломать (нет тестов, неясна логика)
• Баги: исправил одно, сломал другое
• Моральный урон: хочется уволиться

РЕШЕНИЕ (долгосрочное):
• Постепенный рефакторинг (Boy Scout Rule)
• Добавлять тесты по мере работы
• Переименовывать переменные, разбивать функции
• Документировать неочевидные части

УРОК:
Нечитаемый код → технический долг → замедление разработки → деньги компании.
Читаемый код → быстрая разработка → счастливые разработчики → успех проекта.

"Код пишется один раз, читается сотни раз" → инвестиция в читаемость окупается многократно.

СВЯЗЬ С ФОРМУЛОЙ

Эта теорема связана с формулой:

C = A + D + T

где D (Design) включает читаемость:
- Плохой design (нечитаемый код) → C низкое, даже если алгоритм правильный
- Хороший design (читаемый) → C высокое, легко поддерживать

Альтернативная формула: P = S × (1 - B) × M
- M (Maintainability) зависит от читаемости
- Нечитаемый код → M низкая → P (продуктивность) падает
- Читаемый код → M высокая → P растёт

Читаемость = мультипликатор продуктивности команды.

ПРАКТИЧЕСКИЕ СОВЕТЫ

1. ПОНЯТНЫЕ ИМЕНА

   ✓ Переменные, функции: описывают, ЧТО содержат/делают
   ✓ НЕ бояться длинных имен (calculate_user_discount > calc_ud)
   ✓ Константы: UPPERCASE_WITH_UNDERSCORES
   ✓ Классы: PascalCase, функции: snake_case (Python) или camelCase (JS)

2. МАЛЕНЬКИЕ ФУНКЦИИ

   ✓ Функция = 5-20 строк (если больше → разбить)
   ✓ Делают ОДНО (Single Responsibility)
   ✓ "Если функция не влезает на экран → она слишком большая"

3. ИЗБЕГАТЬ ВЛОЖЕННОСТИ

   ✓ Глубокая вложенность (if в if в if в for) = нечитаемо
   ✓ Guard clauses: ранний return вместо вложенных if
   ✓ Вынести логику в отдельные функции

4. CONSISTENT CODE STYLE

   ✓ Вся команда: один стиль (отступы, скобки, naming)
   ✓ Использовать автоформаттеры: black (Python), prettier (JS)
   ✓ Линтеры: eslint, pylint (ловят ошибки стиля)

5. CODE REVIEW

   ✓ Коллеги читают код → если непонятно, просят улучшить
   ✓ Критерий одобрения PR: "Я понимаю, что делает код"

6. РЕФАКТОРИНГ

   ✓ Код стал нечитаемым → рефакторить (не откладывать)
   ✓ "Оставь код лучше, чем нашёл"

7. ТЕСТЫ КАК ДОКУМЕНТАЦИЯ

   ✓ Тесты показывают, КАК использовать код
   ✓ Хорошие имена тестов: test_user_cannot_login_with_wrong_password

КОГДА ТЕОРЕМА НЕ РАБОТАЕТ

⚠ Перфекционизм:
  - Не тратить часы на "идеальную" читаемость
  - Баланс: достаточно хорошо > идеально
  - Shipping > perfection

⚠ Performance-critical код:
  - Иногда оптимизация требует менее читаемого кода
  - НО: изолировать такой код, добавить комментарии
  - 95% кода не performance-critical → пиши читаемо

⚠ Прототипирование:
  - Быстрый прототип (throw-away code) → читаемость вторична
  - НО: если прототип станет продакшеном (часто так) → проблема

⚠ Код-гольф, конкурсы:
  - Цель: минимум символов → читаемость не важна
  - Но это игра, не реальная разработка
